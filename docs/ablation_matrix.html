Shotgun GFP Ablation Matrix

A flag-gated harness and condition set for testing what the active-learning machinery in src/utls.py actually contributes — plus the three problems that make any comparison meaningless until they're fixed.

Target 1× H100 80GB · 12 cores / 24 threads · 240 GiB Stage 1 8 runs Stage 2 15 conditions × 5 seeds

Fix before you measure anything

prerequisites

These aren't improvements to test — they're defects in the measurement apparatus. Running the matrix without them produces numbers that can't be attributed to any condition.

Nothing is seeded

blocks comparison

run_training calls split_data without random=False, so random_state=None (data_loading.py:115). There is no torch.manual_seed, np.random.seed or random.seed anywhere in the repo, and update_state's random.shuffle is unseeded too. setup() sets cuDNN flags but no seeds.

Every run draws a different train/val/pool split. Two runs of the same condition differ, so a gap between two conditions is uninterpretable. Seed everything from one CLI --seed, and pass it into split_data.

The evaluation set changes every round

invalidates AL curves

active_learning rebuilds unlabeled_dataset = Subset(base_dataset, state.unlabeled) after update_state has removed the round's acquisitions, then passes it to eval_round as the test set (utls.py:706-711).

Two things break. Across rounds, the test set shrinks by 96 and systematically loses whichever sequences the acquisition function judged most informative — so a rising R² mixes genuine model improvement with the test set getting easier. Across conditions, each one acquires different points and is therefore scored on a different test set, which makes the whole matrix incomparable.

Carve a frozen held-out test split before round 0, exclude it from the acquirable pool, and evaluate on it identically every round and in every condition.

There is no random-acquisition baseline

unfalsifiable claim

Every condition below is a variation on how to choose sequences. Without a run that spends the same 960-sample budget on uniformly random picks, "active learning helps" has nothing to be measured against — and for point-mutant libraries with a narrow fitness spread, random is a genuinely strong baseline that frequently wins.

This is condition S1-R in Stage 1, and it should be the first thing you run.

Validation set is fed from the acquisition pool

confound

update_state diverts 5% of each round's acquisitions into validation (n_val = max(1, int(0.05 * len(new_samples))), utls.py:255). Validation therefore grows over rounds and drifts toward whatever the acquisition function favours — while being used for early stopping and best-model selection.

So conditions with different acquisition strategies get systematically different validation sets, which changes model selection independently of the strategy's real merit. Either freeze validation up front, or keep the 5% diversion and treat it as part of the condition. Freezing is cleaner.

Early stopping cannot fire during AL rounds

silent no-op

ModelConfig.patience = 20, but AL rounds 1–10 train for epochs = 11. running_patience can only reach 11, so the early-stopping branch is unreachable except in round 0 (99 epochs, via starting_epoch_multiplier = 9).

Not necessarily wrong — but it means "best model on validation" is really "last epoch" for ten of the eleven rounds. Decide deliberately; don't leave it accidental.

mechanism audit

Harness: one code path, flags default to current behaviour

implementation

Don't fork the repo per condition — you'll never keep four branches in sync and you can't diff results reliably. Add one config object whose defaults reproduce today's behaviour exactly, so the original is condition C0 rather than a separate codebase, and each fix is a single flag flip.

# src/configs.py
@dataclass
class AblationConfig:
    # --- acquisition scoring ---
    acquisition:      str  = "uncert_dist"  # uncert_dist | random | uncert | dist | greedy
    normalize:        str  = "minmax"       # minmax | rank
    beta_mean:        float = 0.0            # weight on the unused exploitation term

    # --- batch selection ---
    cluster:          str  = "spectral"     # spectral | kmeans | none
    diversity_input:  str  = "tensor"       # tensor (current, broken) | sequence
    diversity_metric: str  = "kmer"         # kmer | hamming | embedding | none

    # --- training ---
    use_query_weight: bool = False           # honour al_cfg.new_query_weight

    # --- measurement apparatus (see prerequisites) ---
    seed:             int  = 0
    frozen_eval:      bool = False           # fixed held-out test set
    frozen_val:       bool = False           # no 5% diversion into val

Where each flag is gated

  • acquisition, normalize, beta_mean — inside compute_acquisition (utls.py:450). random returns np.random.rand(n), which reuses the whole downstream path unchanged.
  • cluster — replaces the SpectralClustering call (utls.py:581); none assigns every point to cluster 0 so compute_assignments hands the full budget to one group.
  • diversity_input / diversity_metric — get_queried_samples needs the sequence strings, which it currently never receives. Pass pd.concat([train_df, unlabeled_df])["sequence"].tolist() down from active_learning and index it with top_global.
  • use_query_weight — delete the overwriting weights = torch.ones_like(yb) line when true (model.py:340).
  • seed, frozen_eval, frozen_val — setup(), split_data, active_learning, update_state.

One entry point, run_experiment.py --condition C7 --seed 3, resolves the condition name to a flag set, runs it, and appends one row per round to a shared results CSV: condition, seed, round, labeled-set size, and every metric on the frozen test set. That CSV is the deliverable — the existing project/results/ tree is per-run plots and won't aggregate.

Stage 2 — the condition matrix

15 conditions × 5 seeds

Every condition is one flag away from the reference row C1, so each difference is attributable to that one flag. Greyed cells hold the reference value; bold cells are what changed.

Why there are two anchors. C0 is today's code, untouched — including spectral clustering, which may cost hours per run. Making it the reference would force every other condition to carry spectral too, and the matrix stops being affordable on one GPU. So C1 is the same unfixed behaviour with only the clustering swapped for KMeans, and everything varies from that. C1 repairs nothing — it keeps the broken tensor diversity input, kmer, query weighting off. That's deliberate: the reference has to be the unfixed behaviour, or a difference like C3 − C1 would confound the diversity fix with everything else. C0 vs C1 then tells you whether the KMeans swap changed anything, which is what licenses reading the whole matrix as a statement about the real original.

Reading the matrix

  • C1 vs C6 should be identical within seed noise. If they aren't, the no-op finding is wrong and everything downstream needs rechecking. It's a free correctness assertion — include it.
  • C2 vs everything is the only comparison that establishes active learning works at all.
  • C3 vs C1 is the specific question you asked: what does repairing batch diversity buy?
  • C0 vs C1 should also be close. A large gap means clustering choice matters more than any of the fixes, which would be a finding in itself.

Further improvements worth considering

beyond the matrix
correctness

Budget exceeds pool size for 8 of 14 peaks

acquisition_budget_total = 960, but only cgre1338 (8,934), cgre4111 (8,214), cgre132 (4,267), cgre9708 (4,180), cgre2880 (1,780) and cgre900x (1,276) have more than 960 candidates. For cgre985 (466) down to cgre1414 (60), AL would try to acquire the entire pool and the experiment degenerates.

Restrict the AL pool to peaks above ~2,000 rows, or scale the budget per pool. Either way, state the rule explicitly rather than letting it silently degenerate.

performance

Redundant dataset writes inside the per-source loop

torch.save(unlabeled_dataset, dataset_path) sits inside for source in unique_sources in save_metrics, so the same ~100 MB tensor is written once per source, per round. With 15 sources over 11 rounds that's roughly 16 GB of pointless I/O per run — on a shared cluster filesystem, plausibly more wall-clock than the training. Hoist it out of the loop.

metric

Hamming is the better diversity metric here

k-mer Jaccard is what you reach for when sequences vary in length or aren't aligned. Every sequence here is exactly 236 residues, pre-aligned to a common parent, differing at a handful of positions — so Hamming is cheaper, exact, and far more sensitive. The k-mer route compresses a 2-residue and a 4-residue difference into nearly the same number (221 vs 215 shared 3-mers).

That's condition C4. If it wins, drop the k-mer path entirely rather than keeping both.

statistics

Five seeds minimum, and report the spread

With 245 initial labels and 96 acquisitions per round, between-seed variance will be large relative to any effect you're chasing. compute_SE already aggregates across num_runs and prints mean ± SE — it just needs num_runs > 1, which the shipped config never sets.

Prefer 5 independent seeds via the harness over num_runs=5 inside one process, so a crashed run costs one seed instead of all five.

method

Report AL curves, not just endpoints

The interesting result isn't R² after 960 acquisitions — it's the shape of the curve: how fast each strategy climbs, and at what budget it overtakes random. Log every metric at every round against labeled-set size, which is what the shared results CSV is for. A strategy that reaches the same endpoint in 3 rounds instead of 10 is the actual win, and an endpoint-only table hides it.

method

Decide what AL is optimizing for

The current score is pure exploration — uncertainty plus coverage — which optimizes a model that predicts the whole landscape well. The unused mean term would make it exploitation: find the brightest variants. These are different experiments with different success metrics (R² on held-out vs. max brightness found within budget), and the leftover dead code suggests the project has been both.

Worth settling with Jannis before the runs, because it determines which column of the results table is the headline.

infra

Cluster execution

The model is 4.7M parameters and ~19 MB — a single H100 is enormously oversized for one run, and the GPU sits idle during clustering and acquisition. Run 3 array tasks concurrently on the one card (--array=0-74%3, 15 conditions × 5 seeds) and you'll roughly triple throughput at no memory risk.

Cap threads per task (OMP_NUM_THREADS=6) so three concurrent sklearn processes don't oversubscribe your 12 physical cores. num_workers resolves to min(8, 24//2) = 8 per task, which is too many at concurrency 3 — make it a config value.

infra

bf16 instead of fp16 on H100

train() uses torch.cuda.amp.autocast(dtype=torch.float16) with a GradScaler. On H100, bf16 has the same throughput, needs no loss scaling, and removes a class of silent overflow. Also worth clearing the two deprecation warnings (torch.cuda.amp.* → torch.amp.*) while you're in there.

Fixed experimental setup

hold constant

Every condition shares this, so that only the flags differ.

  • Train peak — cgreGFPWT-00 (24,540 rows, the single-parent cgreGFP library).
  • AL pool — cgre1338-06 (8,934) as primary; replicate the winning conditions on cgre4111-12 (8,214) to check the result isn't peak-specific.
  • Frozen test set — a fixed fraction of the pool held out before round 0, never acquirable, identical across conditions and seeds.
  • Budget — 96 × 10 rounds, uniform schedule (get_budget(..., uniform=True), as active_learning already passes). The harmonic-decay branch is currently unreachable; leave it out of scope.
  • Model — AL defaults: hidden_channels=512, depth_conv=5, depth_ffnn=3, epochs=11, starting_epoch_multiplier=9. Note these differ from the non-AL defaults, so AL and non-AL numbers are not directly comparable.
  • Seeds — 0, 1, 2, 3, 4.
